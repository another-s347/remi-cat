# 等待模式源码与轨迹复核（2026-11-01）

结论：等待模式将CLI退出策略、异步工具语义及模型提示耦合在一起。长任务的异常消耗可定位到连续失败调用没有被阻止；现有证据不能把它归因于后台通知重复或单纯的等待时间。

## 实际改变的四件事

1. `process_prompt_message` 把 wait_background_tasks 合入 async_agent。
2. 同函数在 wait_background_tasks=true 时关闭整个prompt的硬编码300秒截止；标志本身没有提供另一个有限时长。
3. agent工具前台等待默认从同步300秒缩短到异步10秒（可由REMI_TOOL_FOREGROUND_TIMEOUT_MS覆盖）。超过阈值后同一个工具任务被提升为后台任务，不是启动第二份执行。
4. runtime注入额外Async tool execution系统提示；后台完成通知可触发后续模型轮次。退出前还有本地后台任务检查。

因此，先前回答“提示词没有更换”不够准确：主profile和工具定义未更换，但增加了异步系统提示。实际保存请求也证实system消息由3条变成4条。

本地等待并不按250ms调用一次模型。app里的250ms循环只检查工具任务状态；模型收到后台结果后的续轮、主动tool_tasks调用、正常执行轮次，才可能产生新的API输入。该标志不能理解成模型停止工作、仅等待一个长命令。

## 116轮案例不是后台通知重放

对026–141响应重新抽取当前输出，得到116个新工具调用ID，参数相同。下一轮输入中能找到全部116个工具结果；没有一个返回后台task_id，都明确包含FAILED与exit101。

失败输出指向模型自己写的tests/basic.rs:247，Command.output().unwrap()获得ENOENT。该测试使用：

    .current_dir(Path::new(file!()).parent().unwrap().parent().unwrap())

当file!为tests/basic.rs时，这一表达式得到空路径。最小Rust复现使用同一表达式，打印resolved_cwd=""，并在Command.current_dir("").output()得到同样的NotFound。测试文件路径拼接错误足以解释现场错误；原样再次执行不会修复它。此源码错误与额外tempfile依赖导致外部离线构建失败是两个独立问题。

116轮输入合计4,154,714，其中未缓存163,162；每次都把既有历史再发给模型。异步提示正文约108个cl100k估算tokens/请求，288个有usage请求累计约31,104个估算tokens；这是文本体积估算，不能当作Kimi分项账单，但不支持把数百万输入解释成一条提示过长。

运行时已经能识别exit非零并展示失败，但这条主流程没有给CoreAgentLoop设置max_tool_rounds。此次记录中没有重复失败保护阻止后续同参调用；上下文窗口预算也不是累计输入预算，不能防止很多个仍低于窗口限制的请求。

## 能与不能推断的结论

- 可以确认CLI300秒硬截止阻碍了长任务，现有等待模式确实允许超过300秒。
- 可以确认模型重复发起了失败测试，框架允许它持续到外部900秒截止。
- 不能证明异步提示本身造成了重复。两批不是相同模型轨迹的成对复放，模式、缓存、执行次序都不同。
- 默认与等待两批正常交付均3/6。延长等待在本批没有带来交付数提升；不能只看默认模式提前停工后的低token数。

## 优化顺序建议（本次未实现）

1. 将运行总时限、是否等后台任务、是否启用异步工具分成独立选项，保留明确的有限预算；等待后台不应隐式更改全部执行语义。
2. 加入重复失败保护：工具名+规范化参数+错误类别/核心错误文本+相关代码版本。重复且代码未变时要求定位错误，继续无进展则停止该路径；对明确瞬态错误允许有上限的退避重试，避免误伤合法重试和长任务状态查询。
3. 分开设置墙钟时间、模型轮次、累计输入预算；记录停止原因。取消/停止不能伪装成完成。
4. 给验证失败建立结构化状态，用于控制流和诊断；保留对模型的关键错误上下文，而非只依赖模型从重复文本中自行跳出。

没有改变产品逻辑，也没有新增模型测试。证据沿用target/token-extended-comparison-2026-10-31/，附本地最小路径复现。
