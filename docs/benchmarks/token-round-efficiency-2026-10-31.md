# remi 轮次效率：逐请求复核

基于同日已完成的 27 次实验，不新增模型调用，不改变产品实现。
原实验见 [token-efficiency-2026-10-31.md](token-efficiency-2026-10-31.md)。

## 结论

默认 profile 长度不是本次额外轮次的主要解释。retry 的轮次差异可以精确对账：

- remi 对 OpenCode 多 18 个主模型请求，其中 10 个是纯 Todo 操作、4 个是缺父目录后的恢复、2 个是没有合并的实现/导出写入、1 个是测试发现空跑、1 个是额外探索。
- remi 对 DeepSeek 多 6 个主模型请求，其中 4 个是父目录恢复、1 个是测试发现空跑、1 个是额外探索。**两者在 retry 都有 10 个纯 Todo 轮次。**
- 缺父目录的恢复还在关闭 Todo、精简 profile 的 retry 中出现：五条 remi retry 轨迹均发生。优先改善工具的一次完成能力，比继续删 profile 更有针对性。

这里的一轮指一次真实主模型请求，包含最后回答；单次请求可以输出多个工具调用。标题等辅助调用单列，不混入主任务轮次。

## 主模型轮次：先统一口径

每类任务两次合计：

| 任务 | remi | OpenCode | DeepSeek Harness |
|---|---:|---:|---:|
| CSV | 30 | 27 | 50 |
| retry | 37 | 19 | 31 |
| 日志定位 | 14 | 10 | 11 |
| 合计 | 81 | 56 | 92 |

OpenCode、DeepSeek 各另有 6 次标题请求，原报告的 API 请求总数仍是 62、98。原来直接比较 retry 的 37/21/33 会把后两者的标题也计算进去；主任务应比较 **37/19/31**。

## retry：额外的 18 轮究竟在哪里

逐个解析 response SSE，重建当前请求输出的工具调用，再人工标注。不能把下一轮 input 中的历史工具调用当成当前轮输出；DeepSeek 的标题还会与主请求并发到达，不能假定第一条就是标题。

| 输出行为 | remi 两次 | OpenCode 两次 | DeepSeek 两次 |
|---|---:|---:|---:|
| 探索/读文件/找测试 | 12 | 11 | 11 |
| 纯 Todo 控制操作 | 10 | 0 | 10 |
| 有效写入实现、导出、测试 | 6 | 4 | 6 |
| 写入失败与建父目录恢复 | 4 | 0 | 0 |
| 执行验证 | 3 | 2 | 2 |
| 最后回答 | 2 | 2 | 2 |
| 主模型请求合计 | **37** | **19** | **31** |

“有效写入”按有生产性文件修改的请求计数，不是文件数。OpenCode 把实现和导出合在同一模型请求内输出两个工具调用，每次任务因此比 remi 少一轮。两者最终都修改相应文件。

### 1. 最稳定的 remi 差异：创建文件要三轮

默认 retry 第一次：

| 请求 ID | 行为 | 结果 |
|---|---|---|
| 013 | `fs_write tests/test_retry.py`，发送完整测试代码 | `No such file or directory` |
| 014 | `fs_mkdir tests` | 创建目录 |
| 015 | 再次 `fs_write tests/test_retry.py` | 成功，再次发送完整测试代码 |

第二次同样发生在 011/012/013。源码的 `fs_write` 明确规定父目录必须存在，`Sandbox::write` 直接写文件；这不是瞬时网络失败，也不是提示里没写清楚。模型仍在五条 retry 轨迹中重复踩到这个契约。

| remi 配置 | 对应请求：失败写入 → 建目录 → 成功写入 |
|---|---|
| 默认第一次 | 013 → 014 → 015 |
| 默认第二次 | 011 → 012 → 013 |
| 关闭 Todo | 009 → 010 → 011 |
| 精简第一次 | 007 → 008 → 009 |
| 精简第二次 | 010 → 011 → 012 |

精简配置没有 `fs_mkdir`，模型改用 Bash `mkdir -p`，仍然经历三轮。说明这部分成本不能靠裁剪工具或缩短提示消除。

OpenCode 的 write 定义明确自动创建父目录，测试中直接成功；DeepSeek 的对应写入也直接成功。remi 默认两次的“失败写入 + 建目录”请求合计携带输入 24,546、输出 1,494 tokens，后续还会重放这段历史。这是请求归属统计，不能直接等同于修复后的净节省量。

**建议：**让创建文件能够在一次调用内完成必要的父目录创建，或提供明确的 `create_parents` 语义，并沿用工作区路径校验。若产品坚持父目录必须显式创建，则至少让目录准备和独立实现/导出操作在同轮完成，避免先发送大段文件内容再失败。前者有更直接的已观测收益来源。

证据：[工具契约](/home/skye/remi-cat/crates/bot-core/src/tools/mod.rs:536)、[Sandbox 写入](/home/skye/remi-cat/crates/bot-core/src/sandbox/mod.rs:295)、`main/remi-retry-1/requests/013.response.txt`。

### 2. Todo 多轮与进度语义问题要分开看

retry 中 remi 每次都是 5 个纯 Todo 请求；DeepSeek 也各 5 个。因此不能把 Todo 当作 remi 相对 DeepSeek 的额外轮次原因。

但是 remi 有更具体的接口/指令问题：默认指令要求逐项进入 `in_progress`，实际 `todo__update` 只改标题；完成接口按单个 ID 操作。本次默认 retry 第二次已在一个请求中调用两次 complete，说明模型和后端能够合并，并不存在“每完成一项必须再请求一次模型”的硬限制。

更严重的是进度不一定真实：

- retry 第一次，Todo 1 是“创建 retry 实现”，009 就完成它，实际实现写入在 010。
- CSV 第二次，003 完成“实现”，004 才打补丁；005 完成“添加测试”，007 才写测试；008 完成“运行验证”，009 才执行验证。

这些轮次付出了成本，却没有提供可靠的执行状态。不能只通过自动完成 Todo 来加速，应先保证状态符合已经完成的动作。

**建议：**统一 Todo 状态接口和提示；允许按阶段批量变更；有依赖的“成功完成”标记应在工具结果确认后更新，尽量附在下一次必要操作中。简单任务可以不强制完整任务清单。关闭 Todo 的单次消融只能支持进一步验证，不能证明应全局删除 Todo。

### 3. 可合并写入被拆开，是决策问题

remi 两次均分别写实现、修改导出、写测试，共 3 个生产性修改请求；OpenCode 将前两项合并，每次只有 2 个。

这两处文件在同一轮已读取，针对不同路径的实现/导出修改可独立发出。remi 轨迹里既有同轮两次 `fs_read`，也有同轮两次 `todo__complete`，源码也支持并行工具执行。因此应改善模型的分组策略，不能诊断成执行器不支持多工具调用。

**建议：**明确鼓励合并已经掌握输入的独立读写；需要依赖返回结果的操作仍分开。不要把“建目录 + 写其下文件”直接作为无依赖并行调用，它们确有顺序依赖。

### 4. 测试发现空跑、过度探索属于共有策略问题

remi retry 第一次先执行 `unittest discover -v`，返回 `Ran 0 tests ... OK`，随后改成显式 `-s tests` 才跑到测试。这里第二次命令是在正确恢复，值得避免的是第一次选错入口，不是删掉验证。

DeepSeek 的 CSV 第二次也出现测试发现后改用明确模块的轨迹；初始 fixture README 又给出了通用 discover 命令。所以这不是 remi 独有的底层缺陷，不能据此增加统一的“少测试”指令。

探索轮次合计是 remi 12、对手各 11，差距只有 1。remi 确实重复列出根目录、读取无关 data 目录；OpenCode 也多次用不同 glob 找不存在的测试，DeepSeek 也重复找测试。**过度探索是三者共有，证据不支持将其列为 remi 最大问题。**

## 其他任务的交叉验证

日志定位两次，remi 都先用默认读取触发超限，再显式请求 32768 继续超限，然后缩小到 16 KiB 左右。提示已建议 `length=23488`，模型仍重试了原范围。32 KiB 默认读取与 24000 bytes 输出限制的内部不协调，至少稳定制造了恢复路径；随后大段日志还进入后续请求历史。

两次共 14 轮，对手 10/11 轮。这里优先应解决有效读取预算，而不是增加一大段“看到错误要仔细看”的系统提示。首次读取是否该改成搜索，属于任务策略；工具默认设置是否会自相冲突，属于可以确定修正的机制。

CSV 的修复/验证轮次不能当作纯浪费。默认 remi 第一次 20 轮通过，第二次 10 轮却失败；后者还有提前完成 Todo 的问题。减少重复失败和控制空转应以独立验收不退步为前提，不能追求最少请求数本身。

## 实施优先级与可验证目标

1. **父目录创建的一次完成能力**：先以五条重复失败为回归样本；验证不再先写失败、不再重复生成整个测试文件。这直接针对 remi 的工具契约摩擦。
2. **读取预算对齐**：默认与显式范围都应符合有效输出上限，避免同一范围反复超限。
3. **Todo 状态正确与批量更新**：先修进度语义，再减少纯控制轮次；不能把“完成”提前放在实际执行前。
4. **独立工具分组及测试入口选择**：通过窄范围策略实验衡量，保持真正的测试和失败恢复。

只按现有两条 retry 轨迹静态计算，消除父目录恢复 4 轮、避免空测试发现 1 轮、合并实现/导出 2 轮，可标出 **7 个候选减少轮次**；37 → 30 只是静态重排目标，未实现也未重新跑模型，不能当作实际收益。Todo 调整另行评估，以免与这些候选重复归因。
